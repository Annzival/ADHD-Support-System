# Grilling 中的 Git 发布规则

本规则用于在持续 grilling 过程中保存已经达成共识的产品与架构决策，使提交可审查、远端有检查点，并避免把尚未确认的想法写入正式历史。

## 授权边界

在 grilling 范围内，Agent 可以自主执行以下操作：

- 创建或切换 `agent/` 前缀的主题分支；
- 暂存本轮已确认决策产生的文档改动；
- 创建 commit，并推送到对应远端分支；
- 创建和更新 Draft PR，包括标题、描述、base 分支以及 Issue/ADR 链接。

该授权不包含：

- 直接修改或推送 `main`；
- 将 Draft PR 标记为 Ready、合并或关闭 PR；
- force push、改写已经推送的历史或删除分支；
- 创建 release、部署应用或发布软件包；
- 把未获用户确认的产品方案写成正式决策；
- 暂存或提交不属于当前 grilling 的用户改动。

上述操作只有在用户另行明确要求时才能执行。

## 从决策到文档

1. 用户尚未确认的候选答案不进入正式 ADR；必要的临时记录只保留在对话或明确标记的待办中。
2. 用户确认决定后，立即更新相应的 `CONTEXT.md`、ADR 或其他设计文档。
3. 固定业务选项、Agent 建议、研究推断和已经接受的决策必须分开表述。
4. 如果后来改变决定，新增决定或将旧 ADR 标记为 superseded；不得通过改写已推送历史掩盖演进过程。

## Commit 检查点

不为每个回答机械地创建 commit。出现以下任一条件时，Agent 自主建立检查点：

- 一组相互依赖的决定已经形成完整且内部一致的结论；
- 单个决定显著改变产品范围、授权边界或架构，并值得独立审查；
- 即将暂停 grilling、结束当前会话或切换到另一个主题；
- 新建的 Issue、PR 或其他工作即将依赖尚未发布的文档；
- 即将进行可能影响当前文档的大范围调整。

每个 commit 只表达一个可说明的意图。提交前必须检查工作树和 diff，只暂存当前范围内的文件，并至少运行空白错误检查、ADR 编号/引用一致性检查以及与改动风险相称的其他验证。

## Push 规则

- 每个通过检查的 checkpoint commit 创建后，立即 push 到当前主题分支。
- 会话结束或长时间暂停前，不应留下只有本地 commit、没有远端检查点的已确认决策。
- 检查失败、文件归属不清或远端出现未知分歧时不得 push；先保留现场并向用户说明。
- 已经推送的错误通过后续普通 commit 修正，不使用 force push。

## 分支组织

- 从 `main` 开始新主题时，先同步远端并创建含义明确的 `agent/<topic>` 分支。
- 当前 Draft PR 的目标与新决定一致时，复用该分支和 PR。
- 当审查问题、主要领域或交付目标发生变化时，创建新的主题分支，避免让一个 PR 无限扩张。
- 如果新主题依赖尚未合并的 PR，可以创建以该主题分支为 base 的 stacked Draft PR；上游 PR 合并后，将下游 PR 的 base 调整为 `main`。
- 如果新主题与未合并 PR 无关，则从最新 `main` 独立创建分支。
- Agent 不自主删除已经合并或废弃的远端分支。

## Draft PR 组织

- 主题分支第一次 push 后，如果还没有对应 PR，创建 Draft PR。
- PR 描述必须说明变更、原因、用户或开发影响、验证方式，并链接相关 Issue 和 ADR。
- 后续 push 自动更新同一 PR；范围发生实质变化时同步更新标题或描述。
- 一个 PR 应围绕一个能够独立审查的问题。PR 达到完整检查点后停止加入无关主题，并提示用户可以审阅。
- 是否转为 Ready、采用何种合并方式以及何时合并，由用户决定。

## 工作树与冲突保护

- 发现不属于当前任务的修改时，不使用 `git add -A`，只暂存明确归属当前 grilling 的路径。
- 当前改动与用户已有修改重叠且无法安全分离时，停止提交并说明冲突。
- 不使用 destructive git 操作，不依赖未解析的通配符确定删除或覆盖范围。

## 进度报告

每次自动 push 后，向用户简要报告分支、commit、Draft PR、验证结果以及仍需用户决定的事项。没有发生 commit 或 push 时，不把普通文档编辑描述为已经发布。
