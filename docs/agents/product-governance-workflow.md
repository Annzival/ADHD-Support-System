# 产品治理与 MVP 构建就绪工作流

## 适用条件：必须显式激活

本文档描述一种可选的 session 工作流，不声明任何 session、Agent 或人类协作者天然拥有“产品治理主线程”身份。

只有满足以下任一条件时，当前 session 才激活产品治理角色：

- 用户在当前 session 中直接明确指定该 session 承担“产品治理与 MVP 构建就绪”职责；
- 启动当前 session 的任务 Prompt 明确指定该职责。

激活只对收到该指令的当前 session 生效。产品治理 session 可以在对话中简称“主线程”，但该称呼只是当前任务的会话路由，不是仓库级身份或长期权限。

以下任何信息都**不能**激活或证明产品治理身份：

- 本文件存在，或 `AGENTS.md`、Issue、PR、commit、分支引用本文件；
- 当前分支名称、工作目录、仓库副本、worktree 或对话标题；
- 另一个 session 的角色、历史对话、摘要、日志、注释或先前任务上下文；
- 某个 Agent 曾经创建、修改或审查过产品治理文档；
- 当前任务涉及产品文档、ADR、Issue 或 PR。

如果当前指令没有显式激活，或无法确认激活来源，默认结论始终是：**当前 session 不是产品治理主线程**。

## 不自动继承

新建、分叉、委派、恢复或并行运行的 session 不继承其他 session 的产品治理角色。除非它们自己的用户指令或任务 Prompt 再次显式激活，否则以下 session 均不是产品治理主线程：

- `research`；
- `prototype`；
- `technical spike`；
- `implementation`；
- `debugging`；
- `code review`。

产品治理 session 为这些任务提供 Prompt、范围或证据回传地址，不等于把产品治理身份传给执行者。执行者也不得从父子 Agent 关系、共同工作目录或共享历史推断继承。

## 不改变人类协作与仓库权限

“主线程”不是人类之间的职位、审批层级、汇报关系或否决权。本文档不要求人类协作者向某个人或 Agent 申请批准，也不改变 maintainer、reviewer、contributor 或仓库所有者的既有职责。

本工作流只帮助整理对话和证据，不授予或撤销任何 Git/GitHub 权限，也不改变现有的分支保护、ruleset、review、merge、push、force-push 或删除规则。所有操作仍受仓库现有规则、平台权限和当前用户授权约束；本文档不能作为扩大操作权限的依据。

## 激活后的职责

当产品治理角色已经被显式激活时，该 session 负责：

- 继续产品 grilling，确定产品范围、边界、优先级和非目标；
- 维护领域模型、统一语言、ADR 及其演进关系；
- 定义 MVP 黄金路径、异常路径和可验收标准；
- 将未决事项分类为阻塞、非阻塞、已推迟或已解决；
- 定义 research、prototype、technical spike 和 implementation 任务；
- 接收各任务提交的证据、限制和结论，判断证据是否足以支持决策；
- 判断 MVP 是否已经构建就绪，或只允许哪些不受阻塞项影响的工作先行；
- 维护相关 Issue、设计文档和 Draft PR；
- PR 达到完整、可审查状态时，明确提醒用户开始审查和 merge。

激活后的产品治理 session 可以执行轻量的只读仓库检查、PR 审查、验收场景编写和决策文档维护。

## 激活后原则上不负责的工作

- 编写产品功能代码；
- 长时间技术调试或具体实现 bug 的定位与修复；
- 运行会产生大量实验日志的构建、打包或兼容性测试；
- 实现 technical spike 或交互原型；
- 通过反复生成真实 LLM 输出代替产品决策。

除非用户明确要求，否则产品治理 session 不开始编码。即使用户允许轻量验证，只要问题的答案依赖真实代码、Windows/Wails 行为、实际 LLM 输出或交互体验，也应转交独立技术执行 session。

## 任务类型的选择

| 类型 | 适用问题 | 主要证据 | 不应混入 |
| --- | --- | --- | --- |
| `research` | 需要通过一手资料、现有项目、规范或 API 文档回答“外部世界是什么” | 带来源的研究文档、事实与推论分离的结论 | 产品代码、未经验证的交互结论 |
| `prototype` | 必须通过可操作界面或状态流体验回答“这样用起来是否成立” | 一次性原型、场景脚本、截图或录屏、观察记录 | 生产质量实现、长期架构承诺 |
| `technical spike` | 必须在真实运行环境或最小集成中回答“技术上是否可行、限制是什么” | 可复现实验、环境与版本、结果摘要、失败证据 | 顺手实现完整功能、擅自改变产品范围 |
| `implementation` | 产品决策和关键技术约束已经明确，需要交付可维护的产品能力 | 产品代码、自动化测试、验收记录、运行说明 | 重新解释或覆盖产品需求与 ADR |

能由可信资料回答时使用 `research`；必须体验交互或状态模型时使用 `prototype`；必须运行真实系统或集成时使用 `technical spike`；不再存在阻塞性产品或可行性未知项时，才定义 `implementation`。

同一问题同时包含“是否可行”和“正式实现”时，拆成 technical spike 与 implementation 两个任务。spike 通过不自动授权后续实现。

## 转交独立 session 的任务契约

产品治理 session 发现需要证据型任务时，不继续以纯讨论猜测答案，而是：

1. 明确任务类型及选择依据；
2. 定义唯一或少量可判定的验证问题；
3. 写明范围内、范围外、验收条件和退出条件；
4. 建议用户新开独立对话和独立分支；未经用户明确要求，不在产品治理 session 代为创建或执行该技术任务；
5. 提供一份已经填好、可以直接复制到新对话使用的完整 Prompt；
6. 要求技术执行 session 把结果保存为仓库文档，并关联 GitHub Issue 和 Draft PR；
7. 要求技术执行 session 回传证据、结论、限制以及可能与现有产品范围或 ADR 冲突的地方。

每项任务至少需要下列定义：

- **验证问题**：任务结束时必须能明确回答的问题；
- **范围内**：允许读取、实现、运行或比较的内容；
- **范围外**：明确禁止顺手扩张的内容；
- **验收条件**：什么证据足以判定通过、失败或部分通过；
- **退出条件**：达到何种时间、尝试次数、证据状态或阻塞条件后停止，避免无限调试；
- **既有约束**：必须遵守的 CONTEXT、ADR、平台范围和技术边界；
- **交付物**：仓库文档、Issue、Draft PR 及必要的最小复现或原型；
- **回传格式**：结论、证据链接、限制、未决风险和对 MVP 的潜在影响。

## 新对话 Prompt 模板

产品治理 session 不得只给出一句任务标题。每次转交时，应根据具体问题填完下列模板，删除所有占位说明后再交给用户：

```text
你正在 ADHD-Support-System 仓库中执行一个独立的【research / prototype / technical spike / implementation / debugging / code review】任务。

身份边界：
- 当前 session 是技术执行或审查 session，不是产品治理主线程，也不继承产品治理角色；
- 当前 session 只能在本 Prompt 的范围内生产证据、原型、实现或审查结论；
- 发现产品范围、领域模型或 ADR 冲突时，只记录并回传，不自行作出产品决策。

任务背景：
【说明它为什么会阻塞或影响 MVP，并链接相关 Issue、CONTEXT 和 ADR。】

需要回答的验证问题：
1. 【可判定的问题。】

范围内：
- 【允许执行的调查、实验、原型、实现或审查。】

范围外：
- 不改变产品范围、领域模型或已有 ADR；
- 不实现与验证问题无关的功能；
- 【本任务的其他明确非目标。】

必须遵守：
- 先完整阅读仓库根目录 AGENTS.md、CONTEXT.md 以及【相关 ADR/设计文档】；
- 在独立分支上工作，不直接修改 main；纯只读 code review 无需为了审查而创建提交；
- 如果结果与产品范围或 ADR 冲突，只记录冲突和证据，按本 Prompt 指定的路径回传，不得自行覆盖；
- 保护用户已有修改，不执行 destructive git 操作，不自行合并 PR。

验收条件：
- 【通过、失败和部分通过分别需要哪些可观察证据。】

退出条件：
- 【达到哪些条件必须停止；遇到哪些阻塞应保存现场并报告。】

必须交付：
1. 在【指定路径】保存一份中文结果文档，记录环境、版本、方法、观察、证据、限制和结论；
2. 创建或更新 GitHub Issue，写明任务类型、验收条件和结果链接；
3. 对产生仓库变更的任务，将交付物提交到独立分支并创建 Draft PR，不标记 Ready、不合并；纯只读 code review 只提交审查报告，不制造空提交或 PR；
4. 如有代码或原型，提供最小复现/运行步骤和与风险相称的验证；大量原始日志不要直接写入产品治理文档，只保留可复现位置和摘要；
5. 最终回报：结论（通过/失败/部分通过）、证据、限制、未决风险、是否发现产品范围/领域模型/ADR 冲突，以及需要显式决策方判断的问题。
```

## 技术执行 session 的反向边界

未被显式激活为产品治理角色的技术执行或审查 session 应遵守以下边界：

- 只执行当前 Prompt 明确授权的 research、prototype、technical spike、implementation、debugging 或 code review 工作；
- 可以读取相关产品文档和 ADR 作为约束，但不能因为读取本文档而取得产品治理身份；
- 可以记录事实、证据、实现限制、风险和候选方案，但不能宣告 MVP 整体构建就绪，不能最终改变产品范围、领域模型、授权边界或 ADR；
- 可以在任务范围内作出可逆的实现选择；需要新增产品能力、数据采集、支持平台或用户权限时必须停止扩张并回传；
- 发现现有 ADR 在真实环境中不可行时，保留可复现证据并按 Prompt 指定路径报告，不直接重写、废弃或 supersede ADR；
- implementation 或 debugging 任务遇到含糊验收标准时，返回提问，不自行补写产品规则；
- code review 只判断变更是否符合既有标准和 spec，不把审查意见提升为新的产品决策；
- 不要求人类协作者获得“产品治理主线程”的额外批准，仍按仓库既有 review、merge 和权限规则协作。

如果任务 Prompt 没有提供冲突回传路径，技术执行 session 应向直接委托者报告；这不等于建立新的审批层级。

## 结果返回后的治理流程

显式激活的产品治理 session 接收结果后依次判断：

1. 交付物是否完整，证据能否复现，事实与推论是否分开；
2. 验证问题是通过、失败、部分通过还是证据不足；
3. 限制是否会改变 MVP 黄金路径、验收标准或非目标；
4. 结论是否引入新的领域概念，或与现有领域模型、ADR 冲突；
5. 应采纳、补充验证、调整范围、推迟还是放弃；
6. 需要更新哪些 Issue、设计文档、CONTEXT 或 ADR。

只有收到显式产品治理职责的 session 才按此流程提出产品范围或 ADR 的变更，并继续交由用户确认。技术 PR 本身不构成产品决策。

## MVP 构建就绪判定

满足以下条件时，显式激活的产品治理 session 才可判断 MVP 整体“构建就绪”：

- MVP 用户、运行平台、范围内和范围外能力已经明确；
- 黄金路径及关键失败/恢复路径已经形成可验收场景；
- 核心领域术语、状态所有权、授权边界和关键 ADR 内部一致；
- 所有阻塞性未决事项已经解决，或有足够证据支持明确取舍；
- 必须依赖真实环境、技术集成或交互体验的阻塞项已经完成相应 research、prototype 或 technical spike；
- implementation 任务能够按依赖关系拆分，每项都有范围、验收条件和退出条件；
- 非阻塞事项已明确推迟到路线图或后续 Issue，不会在实现中被临时决定；
- 支撑上述判断的文档、Issue 和 PR 均可追溯。

如果只有部分不受阻塞项影响的实现可以开始，应表述为“局部构建就绪”，并明确允许开始的范围；不得把它表述为整个 MVP 已经构建就绪。
