# G-01 最小推荐方案：只补存有依据的设备结果

状态：**候选设计，未启用生产接纳逻辑**。依据 ADR-0057、Issue #33、PR #35 的 `7834bdb` 四支诊断。2026-09-24 正常合入 main `7ba8f05` 后提出；不改产品规则。

## 用户会看到什么

推荐：提醒已经提交给 Windows，但用户先点了开始时，允许随后补存那次设备结果，原按钮继续失效、会话不变。无法证实提交先于用户回应时，只记录“设备报告成功、先后未知”，不据此算通知促成了开始。若桌面进程先退出，尚未交回的内存结果丢失，则保留未知，不再显示一遍提醒来补证据。

建议第一版只接纳**同一个 Core 运行期、同一个宿主运行期内**的未保存结果；已由 Core 提交的结果当然可以跨重启按原命令 ID 查询。这样不需要让宿主建立第二个持久事实库，代价是崩溃窗口内有些实际发送只能保持未知。这项跨重启取舍仍须主线程确认，不能从“允许有限追加”自行推导。

## 分工与保存时点

| 时点 | Core（SQLite，同事务） | 宿主（仅本运行期内存） |
| --- | --- | --- |
| 允许发送前 | 验证目标、版本、策略、期限、当前前台；保存一次领取许可，关联数据库、尝试 ID、原目标版本、Core 运行标识、宿主运行标识、领取序号和许可时刻 | 保留许可及原领取命令；领取响应丢失只重试同命令，不直接发送 |
| 调用 Windows 前后 | 不把领取当作已发送 | 保存该许可下的调用前／返回后单调时钟读数、墙钟读数、API 结果、不可变结果 ID；每次许可只调用一次 |
| 提交结果 | 分开保存设备报告、Core 接收时刻、许可引用、可证明的顺序类别；唯一尝试结果约束；状态／事件／处理结果同事务提交 | 重试完全相同的结果命令；不能因用户上下文取消而抹掉已存在结果的传输工作 |
| 用户回应 | 原领域事务继续失效旧操作和未执行尝试，保存 Core 内回应序号／时刻 | 前端正常提交；可附带同进程观测顺序，但不能因此伪造送达结果 |
| 重启 | 已提交许可、结果、用户回应及去重记录保留；产生新运行标识 | 建议清空旧运行工作，不接管孤立领取；没有设备结果的领取保持未知 |

字段名、表／JSON 结构、索引、随机标识生成、故障注入位置都由执行者选择。上述信息只是核对同次许可与设备报告的最低候选，不声称能防御同权限恶意进程。

## 身份依据、顺序和时间限制

许可必须由 Core 在目标仍允许主动呈现时产生，结果必须同时匹配同一数据库／尝试／许可／运行身份，且不能与已保存结果冲突。不能只凭 target ID、成功布尔值或用户点击补存。许可证明曾允许发送，不证明实际调用发生在撤销之前；这两件事必须分开。

推荐只在有**因果顺序证据**时写“发送先于回应”：例如 Core 已提交该设备结果后才提交用户回应；或同一宿主线程已收到 API 返回并保存内存结果，随后转发用户命令，且命令携带该结果 ID、两者来自同一宿主运行顺序。第二种资格是待确认的产品边界，后续需用真实桥接测试证明；来自其他请求通道或存在交错空隙时不得套用。

不要比较两个进程的裸单调时钟数值。宿主前后单调读数只能给出本地调用耗时和本进程顺序；墙钟可能跳变，Core 收到结果的时间只证明接收。推荐保存调用起止区间及其时钟来源，无法定位 Windows 内部实际发送时刻时保留未知，不输出精确“看到通知后多少秒开始”。即使明确 API 返回成功，也只表示原生 API 接纳，不证明用户看见。

“用户先回应”有两种不同事实：实际 Windows 调用完成、结果传输较慢；以及用户已经回应后 Windows 调用才完成。现有四支诊断把发送成功作为回调输入，不能区分两者。推荐第二种及无法区分的情况可以保留有许可的设备结果报告，但将先后／机会资格保留未知；**是否允许这种不确定顺序的追加，是主线程需确认的取舍**，不能由字段设计决定。

## 六种事件顺序

| 情况 | 已有证据 | 候选行为（尚未成为验收答案） |
| --- | --- | --- |
| 正常回执 | 四支诊断第一支：领取→成功回调→回执提交→用户开始，当前 delivered | 保存结果与接收时间；凭 Core 提交顺序确定报告先到，真实发送时间仍不能用接收时刻代替 |
| 用户先回应 | 第二支：回调内提交用户开始→回调返回成功→回执 409 | 检查许可后追加设备报告，不动会话；不能从该回调的控制顺序宣称真实发送早于回应 |
| 请求丢失 | 第三支：回调成功→结果请求未到→用户开始，当前取消后 pump 停止 | 同运行期保留原结果重试；匹配许可后追加一次，先后依据不足则未知 |
| 响应丢失 | 第四支：结果已提交→响应丢失→用户开始 | 原命令重试返回既有结果，不新增事件或机会；此幂等能力已有实测 |
| Core 重启 | I-01 已证实新令牌／同库恢复；未验证候选许可协议 | 推荐未提交旧运行结果不跨期接纳；已提交结果按原 ID 返回；未来若要扩大，另需明确跨期身份和撤销边界 |
| 宿主重启 | I-01 已证实不接管无本地历史的领取；未验证候选结果协议 | 推荐内存中未提交结果不恢复，保持未知；不因缺回执重发；不新增宿主持久日志 |

## 不重复、不复活

发送工作与结果交回工作分开：前者要求当前许可，后者只能追加既有调用结果。旧用户命令继续校验当前版本，历史结果接口不能执行开始／改期等动作。一个尝试最多一个不可变设备结果；同结果 ID 返回原值，换内容拒绝，同一逻辑干预最多一个机会记录。结果不更新已解决干预到 pending、不产生调度、不移动当前会话。所有联合保存仍由 Core 事务负责。

## 主线程需要确认的具体后果

推荐接受以下三项作为最小版本的行为边界（本提案不视为已接受）：

1. 同一运行期内，有 Core 许可和同次 API 结果时可以追加；顺序无法证明也可保留设备报告，但机会资格与延迟未知。结果是事实不被丢弃，也不虚增“通知促成开始”。
2. 不通过墙钟大小认定精确发送先后，只接纳上述可证明的因果顺序；其余保留未知。结果是统计不完整，但不会伪精确。
3. 未提交的结果不跨 Core／宿主运行期接纳；已提交结果仍可跨重启重试。结果是崩溃前的部分发送无法补证，但无需宿主持久事实库。若希望跨重启补存，需另定接纳边界，不是单纯加一个文件。

可逆技术细节不提交给用户选择。需要确认的是哪些事实会保存、哪些仍未知，以及崩溃时接受多大证据缺口。

## 后续最小验证（本轮只读分析，未新增实验）

若主线程认为因果顺序能力需要先验证：只在独立诊断中为现有 pump/HTTP 桥增加运行标识与内存顺序日志，控制六种顺序及两个重启点；问题是“能否关联同次许可，并区分确有因果依据与无依据”，不是“是否应该接纳”。不接入生产命令白名单、不修改 SQLite 权威记录或正式回执守卫。输出脱敏关联／先后矩阵后停止；任一调试路径三次无新证据即停止，不借实验启用规则。Windows API 的发生时间证据仍需实机，Linux 只能证明协议和顺序记录机制。
