## 回执交错的最小复现

方法：真实 Python Core、SQLite 临时数据库、HTTP、Go `deliveryPump`；可控领域时钟固定为 100，夹具 T0=99、D=60、W=1000。使用宿主现有发送器，仅将原生提交替换为返回成功的回调，在指定边界提交用户开始命令。此处“呈现成功”是测试输入，不是 Windows 原生通知已实测的结论。

各支步骤：首次尝试 pending/v1 → 宿主领取 claimed/v2 → 呈现回调一次 → 按表中顺序提交回执与用户开始 → 三次新快照驱动 pump → 显式重试相同回执命令 → 核验旧用户上下文。

| 顺序 | 观察到的送达记录 | 相同回执命令再次提交 | 成功事实 |
| --- | --- | --- | --- |
| 回执先提交，再用户回应 | delivered/v3，delivered_at=100 | 200，原处理结果 | 有 delivery_result_recorded |
| 呈现回调内先提交用户回应，再返回呈现成功 | cancelled/v3，delivered_at=null | 409 stale_context | 无 delivery_result_recorded |
| 呈现后回执请求丢失，再用户回应 | cancelled/v3，delivered_at=null | 409 stale_context；pump 见取消后停止回执工作 | 无 delivery_result_recorded |
| 回执已提交但响应丢失，再用户回应 | delivered/v3，delivered_at=100 | 200，原处理结果；pump 按原 ID 重试 | 有且仅有一次 delivery_result_recorded |

四支均只有一次呈现、一个执行中会话和一个检查点（due_at=160），检查点引用同一会话；原开始调度 fired、新检查调度 scheduled；无执行结果证据、现实开始／结束仍未知；旧用户上下文均 409。显式回执重试前后的快照完全相等。完整事件、对象版本和引用在受控原始输出中，脱敏摘要见 [interleaving.json](mvp-deterministic-branches-recovery.interleaving.json)。

当前机制：`Core.cancel_deliveries` 将 pending 和 claimed 都取消；用户开始同时将干预 pending/v1 解决为 resolved/v2。回执仍引用 delivery/v2、intervention/v1，先被送达记录版本守卫拒绝。即使只改送达版本，干预版本守卫仍会拒绝；宿主也会在看到取消后终止回执工作。不能以单独“重试更多次”解决。

没有发现两会话或半更新；问题是原生成功输入与持久送达事实是否允许在这个顺序下分离。开始成功不证明它是由通知促成，也不能从用户回应倒推出成功送达。

## 待治理判断：G-01

这是一处待解释的规格边界，**尚未认定现有 ADR 必然互相冲突**：

- A02 要求“对应干预及送达尝试身份有效”，通用规则要求预期状态版本校验。现有实现因回应后版本变化拒绝迟到回执，符合严格版本守卫的解释。
- ADR-0052 及领域模型规定回应取消“尚未执行的送达尝试”；已经呈现、回执未提交的尝试是否仍属于该集合未明确。ADR-0016 还要求分别保存送达与回应事实。
- 若在回应后补记送达，必须明确这是历史设备事实的特殊接纳边界，不能因此恢复旧用户操作、调度或再次呈现。规格未规定其接纳资格、时间依据，以及机会记录如何处理回执在进入会话之后到达的情况。

候选处理（均未实施）：

1. **仍拒绝迟到回执**：当前版本守卫不变；明确原生呈现与 Core 确认送达不保证一致，未确认呈现只保留诊断、不计机会。需要治理明确接受此语义及证据限制。
2. **有限追加设备呈现事实**：只针对先前合法领取且可关联的同次尝试，允许保存已经发生的呈现结果；已解决上下文仍不可操作、不重新调度、不重复计数。需要治理明确身份／版本例外、时间依据、失效／重启和去重规则，然后再实现并验证。

需要决策的是“上述第 2/3 行已呈现但尚未被 Core 确认的尝试，回应后是否接纳其历史回执，以及依据是什么”。本 session 不替治理选定，不新增补偿规则或放宽旧操作权限。

任务 Prompt 明确要求此类歧义保存证据后回传。本轮据此在产品编码前退出；独立的不受影响工作仅完成覆盖盘点和 I-01 回归。没有将 G-01 宣称为所有其他转换的技术依赖；后续可在明确协调后继续不依赖它的工作包，但完整验收不能绕过它。
