# 第一个 MVP 验收场景

## 地位与范围

本文是 B-04 的可测试规格，不是测试执行报告。依据为已合并 PR #28（`930746d`）中的[构建就绪范围](mvp-build-readiness.md)、[领域模型](mvp-domain-model.md)、[转换矩阵](mvp-domain-transitions.md)及 ADR-0004、ADR-0008、ADR-0043～0056。没有实现这些场景，也没有因为文档存在而获得功能 PASS。

首个 MVP 必须包含完整方案导入与审阅的设置切片，以及确定性的执行闭环。开发可用预置方案先贯通执行闭环，但正式 dogfooding 前必须通过真实导入、审阅、最终确认；脚手架不能代替设置验收。

每个表格行是一项 Given–When–Then 场景；“分别”列出的条件作为参数化用例逐项执行，不可只挑一项通过。引用的 S / A / E / R 编号指转换矩阵，不是 API 名称。实现可以选择内部结构、测试框架和控件，不能改变断言。

## 公共前置与正确性判据

- 单用户、Windows 10 22H2 x64；默认 Python Core 在本机，SQLite 是唯一权威状态源。Linux 可以验证确定性领域与协议行为，不能替代真实 Windows 桌面验收。
- 领域测试使用独立测试数据库、可控制时钟和可记录送达尝试的替身，不以真实等待来模拟多日或期限，也不访问用户真实方案数据库。
- 固定夹具：方案版本 P、行动 A、安排 a、计划开始 T0、已确认时长 D、宽限 G。除被测条件外，安排有效、无其他活动会话、主动联系被允许。窗口结束 W 晚于被测检查时刻；需要缺省期限时显式去掉窗口或估时。
- 每项成功断言同时检查用户可观察结果和 Core 权威状态：对象身份／版本、引用关系、活动会话数、当前检查点数、调度有效性及产生的事实。检查前后差异，而不是只检查 UI 文案或返回成功码。
- 失败断言要求该命令没有权威半更新或成功事件；诊断日志与拒绝记录可保留。取消只保证该操作不改变状态，不阻止期间发生其他已合法到期的转换。
- 相同命令 ID 重试（包括成功提交但响应丢失）返回原结果；不同命令仍须校验当前版本。全部联合转换适用 AT-01～03。
- 领域事件不自动等同于执行结果证据。未知不等于没执行；送达不证明用户在场；现实开始／结束时刻不能用点击时刻或计划时刻填充。
- 除首次开始及一次允许的较弱跟进、检查点及一次较弱确认外，不得通过恢复、重启或多个载体增加主动次数；恢复只呈现已确认的一次性上下文支持，不补发旧提醒。

## 一、设置切片（SET）

| ID／来源 | Given（给定） | When（当） | Then（应当） |
| --- | --- | --- | --- |
| SET-01 / S01～05 | 未启用方案；提供包含明确行动和时间的文本／Markdown | 导入、生成草案、逐项确认首项行动及时间，再最终确认 | 原文先保存；工作区可追溯原文／派生／缺口；最终确认前无权威安排；确认后同事务发布 P、设当前版本、建立 A 与 a，进入等待开始干预 |
| SET-02 / S02、03 | 原文缺少足够具体的行动或时间，但已有用户目标 | Agent 提议拆分／时间，用户编辑并逐项确认 | 派生内容标注来源与假设，不自行新增目标、截止日期或优先级；最终确认展示来源区别及保留不确定项 |
| SET-03 / S03 | 正在处理或审阅，尚未最终确认 | 保存退出，再重启并返回 | 已保存原文与草案可继续；不自动启用、不调度；这不算设置完成或一次成功进入 |
| SET-04 / S03、05 | 分别存在关键缺口、首项行动未确认、时间未确认 | 尝试最终启用 | 拒绝启用、保留草案，无权威方案或安排半成品；仅非关键未知不阻止合法启用 |
| SET-05 / S05 | 首项行动和时间已明确确认，无预计时长及窗口 | 最终确认 | 允许启用；首次进入会话再按 EX-02 确认时长，不制造没有检查点的会话 |
| SET-06 / S04 | 草案引用原文 v1 | 用户保存 v2，随后尝试使用 v1 草案或接收其迟到结果 | v1 草案／未确认建议被取代；旧结果不能充当 v2 的有效草案；需新版生成或审阅后再确认 |
| SET-07 / S06 | 设置未完成，存在已保存原文及可能的草案 | 生成失败／模型不可用，然后重试或更换模型配置 | 原材料与已保存草案保留，设置显示未完成，不因失败或换供应商自动启用；不要求迁移权威状态到模型服务 |
| SET-08 / S05、ADR-0043 | 最终确认界面打开后来源版本已变化，或事务写入故障 | 提交启用 | 整次失败；无新版本指针、孤立行动或先行调度，仍可回到草案继续；适用 AT-01、02 |

## 二、开始与确定性分支（EX）

| ID／来源 | Given（给定） | When（当） | Then（应当） |
| --- | --- | --- | --- |
| EX-01 / A01、02、05、E04～06 | 已启用 P/A/a 且 D 已适用确认，用户能操作 PC | T0 到达、成功送达，用户立即开始；随后完成并完成／跳过收尾 | 唯一逻辑开始干预；会话与首次检查点原子建立；不周期性追问；报告完成后等待收尾仍占位置；收尾后证据固化、释放位置，系统能继续调度 |
| EX-02 / A04、05 | 有效开始干预，没有适用的确认时长 | 分别仅打开入口、取消、确认本次 D 与检查时间 | 前两者不建立会话／检查点，干预未决；确认后两者同时建立，仅此时计入明确进入行为 |
| EX-03 / A06 | 有效开始干预；即便安排已有估时，实际开始未知 | 选择“我已经开始”，确认从现在起多久后检查 | 同事务建立会话／检查点，来源区别于“立即开始”；实际开始仍未知，不要求补填大致开始时间；取消按 EX-02 |
| EX-04 / A07、E05、06 | 无活动会话，开始上下文有效 | 选择“我已经完成”，再完成或跳过收尾 | 记录报告并结束安排／干预，回顾式会话直接等待收尾、无检查点；不伪造时间，不计入促成进入；收尾后固化结果并释放位置 |
| EX-05 / A08 | a 及其干预有效 | 用户确认改到具体时间 | 原子结束 a 为已改期、建立同一行动的后继安排；旧时间／引用保留，旧操作和待送达失效；失败不只结束旧安排 |
| EX-06 / A09 | a 有效，另有其他已确认安排 | 用户选择今天不做 | 只结束 a 并记录本次不执行决定；A 未完成、方案不变；不自动顺延、不生成次日安排、会话、收尾或包；其他安排时间不因此变化，不宣称后续计划仍可行 |
| EX-07 / A01～03 | 同一干预在多个载体显示，首次送达后未回应 | 重复调度、重复回执，再到宽限结束 | 干预身份不变；同次多载体不增加尝试数；最多一次较弱跟进，无第三次；合格机会不重复计数 |
| EX-08 / A03 | 首次送达后始终未明确回应 | 跟进时分别处于安静时段、PC 离线、下一工作已开始 | 跟进失效，不在条件消失后补发；不把未回应记录为拒绝、失败或没有执行 |
| EX-09 / A10 | 开始干预未决 | 分别到达 W、无窗口时 T0+D、两者皆无时本地次日零点 | 按优先序过期；此前被动保留，不新增显著性变化；到期关闭原操作，无首个 MVP 补记入口，结果未知；期限早于宽限时不再跟进 |
| EX-10 / R08 | 旧未决开始界面未到期，新安排到达 | 无活动会话时观察，再在有活动会话夹具中重复 | 旧界面在主窗口保留至原期限，停止旧置顶和跟进；置顶分别显示最新到期行动或活动会话；不能同时建立两个活动会话 |

## 三、检查点、收尾与历史（SES）

| ID／来源 | Given（给定） | When（当） | Then（应当） |
| --- | --- | --- | --- |
| SES-01 / E01、03 | 执行中会话及唯一当前检查点 c1 | 到点，用户继续并确认下一检查时间，再重复同一命令 | c1 记已回应并继续，唯一后继 c2 保留链；会话 ID 不变；重复不生成 c3；不覆盖原时间，不自动周期续行 |
| SES-02 / E04 | 会话执行中，分别在检查点前／到点后 | 用户报告完成／暂停 | 立即失效旧检查点，会话进入等待收尾且继续占唯一位置；旧继续操作无效，第二会话创建拒绝 |
| SES-03 / E05、ADR-0044 | 等待收尾，用户已报告完成 | 明确确认全部完成／细化为部分完成 | 保留原报告并固化最终证据；全部完成只固化确切版本行动，部分完成不标整个行动完成；历史不因后续方案版本变化被改写 |
| SES-04 / E05、06 | 已明确暂停，等待收尾 | 完成收尾、显式跳过、关闭收尾界面，分别执行 | 原子保存最小证据与恢复包、结束会话并释放位置；未提供的时长、进展细节等仍未知，不追问可选字段 |
| SES-05 / E07 | 已报告完成／暂停，等待收尾且未操作 | 分别到原窗口结束、下一工作需成为前台、无前两者时本地次日零点；多边界时取最早适用者 | 幂等自动跳过，按原明确报告保存最小事实和必要包；无额外提醒，不凭空补实际时长、精力或进展 |
| SES-06 / E02、08 | 检查点已送达，持续无明确回应 | 一次较弱确认后，再达到 W；无窗口的夹具达到检查点日期次日零点 | 此前仅被动保留三类操作；到期结束跟踪释放位置，结果未知，不收尾、不生成结果证据或包；不再主动核对 |
| SES-07 / E09 | 有已固化结果事实 | 用户明确提交更正内容和原因 | 追加带时间的更正并保留原事实；不能改写方案／原证据或由 LLM 自动纠正；对已确认完成行动的恢复请求按更正后的明确事实校验 |

## 四、恢复与重启（REC）

| ID／来源 | Given（给定） | When（当） | Then（应当） |
| --- | --- | --- | --- |
| REC-01 / R01、02 | 已保存未来安排，且离线错过一项主动尝试 | Core／PC 恢复并重复恢复检查 | 仍有效调度恢复；错过尝试失效不逐条补发；原行动保留；有未收束来源时最多一个未决恢复记录，来源不变复用 |
| REC-02 / R01、A10 | 已送达的未决开始界面，在重启时分别未到／已过保留期 | 重启并读取同一数据库 | 未到期恢复被动界面，已过期关闭原操作；均不把旧尝试补发；不把过期等同于丢弃行动 |
| REC-03 / R03、E08 | 旧执行中会话，分别有未来检查点／有效被动核对／核对期限已过 | 重启并继续 | 前两者恢复同一会话与有效上下文，不重新计时或新建会话；第三者幂等结束未知跟踪，不生成包或结果证据 |
| REC-04 / E07 | 等待收尾，分别未到／已到自动跳过边界 | 重启两次 | 前者仍等待且占位置；后者仅一次自动跳过并固化最小事实，不重复证据／包 |
| REC-05 / R04 | 暂停后已有未使用包 p，无活动会话、行动未完成 | 确认从现在起的剩余时长并恢复，再重复请求 | 同事务创建当前时间安排、新会话、首次检查点并将 p 标记被此会话使用；原会话不重开；再次暂停形成新包并保留接续关系 |
| REC-06 / R04、05 | p 指向旧方案版本，当前方案不同 | 分别选择旧断点、按当前计划继续 | 旧断点新会话仍引用旧行动且不移动当前版本；当前计划选择将旧包未使用归档，保留暂停事实，不写成失败／放弃；LLM 不匹配或迁移新旧行动 |
| REC-07 / R04、ADR-0050 | 分别为已使用包、已归档包、明确已完成行动、已有活动会话 | 尝试恢复该包 | 拒绝；不消费包或生成另一会话，不重开历史会话 |
| REC-08 / R06、07 | 只有错过开始记录，没有执行开始证据 | 打开恢复入口，选择暂不决定，重启后再打开被动入口 | 不声称存在执行断点；提供“处理上一项”而非虚构接续；停止主动呈现并保留安静入口；再次处理校验最新来源，不重启催促 |
| REC-09 / R02、ADR-0053 | 已呈现恢复上下文，来源会话／包／安排／当前方案版本之一改变 | 用旧上下文操作，再读取现状 | 旧操作拒绝；旧记录失效，仍需支持才取得新记录；主窗口和通知不拥有各自可修改状态 |
| REC-10 / R09、ADR-0056 | A 仍执行中、未到跟踪截止，B 当前适用；恢复上下文有效 | 明确确认切换及 B 检查时间 | 一个事务结束 A 跟踪、失效旧核对、建立 B 会话／检查点并保存恢复选择；仅 B 占位置；A 退出原因为用户切换，结果未知，无旧收尾／结果证据／包 |
| REC-11 / R09 | 同 REC-10，无其他独立合法转换 | 分别取消、未确认检查时间、注入保存失败、成功后重试同一命令 | 前三者无部分切换，A 原状且无 B 半会话；最后者返回同一 B；若期间 A 已合法进入等待收尾，旧请求拒绝，不能覆盖明确报告 |
| REC-12 / R09 | REC-10 已提交但响应丢失 | 重启并重试原命令，再操作旧通知或旧检查点 | A 仍结束跟踪，B 及检查点恢复；不重开 A、不再建 B，不重复事件或主动送达 |

## 五、跨场景原子性与模型边界（AT）

| ID／来源 | Given（给定） | When（当） | Then（应当） |
| --- | --- | --- | --- |
| AT-01 / ADR-0055 | 分别准备方案启用、开始、回顾式完成、改期、今天不做、续行、收尾、恢复包使用、R09 切换 | 在每类事务的联合写入之间注入故障／提交前受控退出 | 同一数据库恢复后为完整旧状态，无部分状态、成功事件或调度；未消费依据仍在；结果与原命令原子性一致 |
| AT-02 / ADR-0055 | 上述每类命令已经成功提交、响应尚未收到 | 丢失响应、重启、用同一命令 ID 重试 | 返回第一次结果；对象身份、事件和调度数量不额外增加；不靠全量事件重放重建状态 |
| AT-03 / 非法转换表 | 两个不同命令同时使用同一预期版本，分别测试开始／改期、续行／完成、恢复／恢复及切换／完成 | 让两个请求竞争提交，再点击过期载体 | 以当前状态版本校验，不能产生互相矛盾的双成功；活动会话至多一个，已失效操作无权威副作用 |
| AT-04 / ADR-0004、0055 | 已保存方案、安排、会话、包、干预；备好切换前身份与状态快照 | 更换 API key／模型／供应商配置，再令模型不可用并使用确定性执行操作 | 权威身份、历史及可继续处理状态不因换模型丢失；确定性开始、改期、今天不做、续行、暂停、收尾和恢复仍按规则工作；仅设置生成失败按 SET-07 |
| AT-05 / ADR-0004、0008 | LLM 输出含建议动作，客户端或桌面壳有本地 UI 状态 | 返回模型内容、关闭／重开客户端或令 Core 不可用 | 建议不直接写权威状态；重连读取 Core，不靠壳或供应商“恢复”第二套状态；Core 不可用时不能显示领域提交成功 |

AT-04 的确定性故障测试可用替身自动化；实际供应商切换还需在设置功能完成后用两个已配置的供应商适配执行一次集成验收，保留脱敏状态快照与结果。更换凭据必须使用测试配置，不提交 key 或原始模型隐私输入。它是实施验收，不要求先穷尽模型效果或重新启动已推迟的完整阻碍支持 V-07。

## 六、桌面与协议集成（DESK）

| ID／来源 | Given（给定） | When（当） | Then（应当） |
| --- | --- | --- | --- |
| DESK-01 / ADR-0008、V-01R | 正式桌面集成运行于锁定 Windows 环境 | 再次启动、关闭主窗留托盘、关闭置顶小窗后从托盘恢复 | 单实例；托盘常驻；小窗可重新显示且置顶；壳不新增领域权威状态或规则 |
| DESK-02 / V-01、V-03 | 正式构建配置了开机启动并有已持久状态 | 按实机验收步骤重启 PC，再受控终止 Core | 自启动及受限进程守护按设备职责工作；恢复同一 SQLite 身份，无重复宿主／Core；领域恢复按 REC，而不是由壳执行调度 |
| DESK-03 / V-02 | Core 仅监听回环地址，运行期令牌和端口已交接 | 测 HTTP / WebSocket 有效、缺失、错误、旧令牌；重启 Core 后重连 | 未授权拒绝；新运行使用有效发现信息；旧连接不能继续冒充就绪；客户端不直接读写 SQLite，无公网监听 |
| DESK-04 / V-01、V-05 | 已有真实安排的通知、主窗口和小窗 | 点击有效通知，再点击已改期／已解决对象的旧通知 | 有效通知返回正确对象上下文；旧操作被 Core 拒绝并显示当前上下文，不造成重复会话；实际 Windows 焦点／通知行为有实机记录 |

这些是生产集成完成时的回归验收，不否定门槛 5 已接纳的 spike 证据，也不允许直接拿旧 spike 的 PASS 替正式构建填写 PASS。Windows 不可用时记录 BLOCKED；Linux／mock 成功只能证明其测试层面的结果。
