# 第一个 MVP 构建就绪门槛

> 盘点日期：2026-08-13
>
> 当前结论：**未达到可以正式构建的状态**
>
> 维护范围：第一个可验证的端到端垂直闭环，不用于穷尽 v0.1 或未来路线图需求。

## 使用方式

本文件是产品治理检查点，不是产品领域 ADR。每完成一项已确认决定或收到一项 spike / prototype 证据后，都要更新：

1. 六项门槛的状态与证据；
2. 全部未决事项的四类归档；
3. 唯一最高优先级的主 grilling 阻塞项；
4. 可以并行启动、但不能冒充已实现功能的验证任务。

状态只使用：

- **满足**：已有明确决定和足够证据；
- **部分满足**：已有约束，但仍缺少会改变首个垂直切片的信息；
- **未满足**：尚不能据此定义或验收首个垂直切片；
- **等待验证**：问题已被正确分流，必须由独立 spike 或 prototype 提供证据。

达到所有门槛时立即暂停 grilling，并输出构建交接报告。门槛未全部满足，不妨碍独立技术验证先行；验证代码和结果不能计作 MVP 功能完成。

## 尚未确认的候选核心闭环

以下内容只用于说明当前最高优先级决定的形状，**不是已经接受的范围**：

> 对已经拥有明确方案、但难以按计划启动的成人 ADHD 用户，状态持久的 PC 执行智能体在约定时间主动呈现一个下一步行动，并提供低成本的开始、缩小或改期分支，能否让用户更快形成明确的执行选择，同时不增加主观压力或削弱自主感？

候选黄金路径为：

```text
已有且已确认的下一步行动
  → 用户确认执行时间
  → 到点产生开始干预
  → 用户选择立即开始，或在阻碍支持中接受一个缩小后的步骤
  → 建立执行会话与一个会话检查点
  → 用户报告完成或暂停并保存恢复包
  → 收尾确认保存执行证据并退出本次闭环
```

候选必要异常仅包括：

- 用户未回应开始干预，系统停止主动跟进并保留/过期正确的被动入口；
- 模型不可用，确定性开始、改期、暂停和退出操作仍然可用；
- Core 或 PC 重启，权威状态和调度可恢复，过期干预不补发；
- 非法或基于旧版本状态的转换被拒绝，权威状态不被破坏。

多日重新进入、完整方案导入、日终复盘、剩余精力、邮件再触达等已确认能力是否进入后续切片，不影响上述候选闭环能否先被构建和验证。

## 全部未决事项的四类归档

### MVP 阻塞

这些问题会改变首个垂直切片，只有它们可以占用主 grilling 流程，并严格一次处理一个：

| ID | 未决事项 | 为什么阻塞 | 解决方式 |
| --- | --- | --- | --- |
| B-01 | 确认一句话核心产品假设、目标用户、首要场景、成功标准维度和明确不做项 | 不知道第一个切片究竟要证明什么，无法判断后续对象和场景是否必要 | **继续 grilling**；当前最高优先级 |
| B-02 | 固定唯一黄金路径和最小必要异常集 | 无法确定首个切片的入口、终点和裁剪边界 | B-01 后继续 grilling |
| B-03 | 为 B-02 建立最小领域对象、权威状态、命令、事件和状态转换 | 实现者无法区分合法转换、未知状态和恢复状态 | B-02 后使用 domain-modeling；必要时新增产品状态模型，只有满足 ADR 条件时才新增 ADR |
| B-04 | 把黄金路径与异常路径写成 Given–When–Then 验收场景 | 无法判断实现是否正确，也无法约束 spike 之后的 implementation | B-02、B-03 后编写验收文档 |

### 实现中再决定

下列选择可逆、成本较低，或不会改变首个闭环，不得阻塞开始编码：

- Wails 前端所用的具体组件库、CSS 方案、目录组织和页面布局；
- 主窗口、置顶小窗和卡片的视觉样式、图标、动画细节及非关键文案；
- HTTP 资源命名、WebSocket 消息命名、Python 包布局和内部模块边界；
- SQLite 访问库、迁移工具、表名、索引和日志轮转细节；
- 端口和临时令牌的具体编码格式，以及验证通过后的默认配置值；
- 模型供应商、模型名称、API key 配置界面和开发期默认模型；权威状态与供应商无关的约束不变；
- 安装包、自动更新和诊断日志导出体验；在首次可运行切片之后、公开分发之前补齐；
- 开源许可证、贡献模板、公开 demo 与作品集包装；必须在对外宣称可复用的开源发布前决定，但不阻塞首个闭环编码；
- 成功指标的埋点存储和可视化方式；指标定义本身属于 B-01，不能延后。

### 需要技术或交互原型验证

这些事项可能阻塞构建就绪门槛，但不得继续占用纯讨论；每项都由独立 session、Issue、分支和 Draft PR 产出证据：

| ID | 验证事项 | 当前能否开始 | 与产品边界的关系 |
| --- | --- | --- | --- |
| V-01 | Windows 10 22H2 x64 上 Wails v3 的托盘常驻、置顶小窗、开机启动、可交互通知和 Python 进程守护（Issue #11） | **可以立即开始** | 只验证桌面宿主；不得把调度、领域状态或 LLM 放入 Wails |
| V-02 | Wails / 桌面客户端与 Python 智能体核心的 localhost HTTP/WebSocket、端口发现和临时令牌 | **可以定义后开始** | 使用最小假数据协议，不替 B-03 决定领域 API |
| V-03 | SQLite 持久化、Core 重启和 PC 重启后的状态、调度与失效干预恢复 | **可以定义后开始** | 使用最小合成状态；领域含义最终受 B-03 约束 |
| V-04 | 系统通知操作能否返回正确的本机应用上下文 | **与 V-01 一并验证** | 验证设备桥接和深链，不在桌面宿主保存上下文状态 |
| V-05 | 恢复干预在置顶小窗、系统通知和主窗口之间的本机载体映射（Issue #7） | **等待 V-01 / Issue #11 证据后做低保真交互原型** | 固定操作是确定性能力；需要缩小步骤时才进入阻碍支持 |
| V-06 | 如果黄金路径包含阻碍支持，真实 LLM 生成的首个缩小步骤是否足够小、可执行且不越权 | **等待 B-01、B-02 后定义 prototype / eval** | LLM 只能生成建议，不能直接修改权威状态 |

V-01 是当前可以最先并行启动的验证任务，完整任务契约和新对话 Prompt 见 [Windows/Wails 薄桌面宿主能力验证计划](../spikes/plans/wails-v3-windows-thin-host.md)。它不依赖尚未确认的核心假设，也不会把 Wails 提前确定为正式桌面宿主；通过只表示五项能力在固定环境与版本下可行。

### MVP 后

以下能力保留既有决定或路线图价值，但不应阻塞第一个垂直闭环：

- Web/PWA、手机原生客户端、多端同步、多用户、公网访问和常开自托管服务器；
- Windows 11、其他 Windows 架构、macOS 和 Linux 的支持承诺；
- 真人或 AI body doubling；
- 微信、QQ 等即时通讯渠道及其账号、审核、限流和送达集成；
- 关机期间仍可靠送达的邮件再触达、邮件深链和跨设备认证；v0.1 已接受的本机尽力发送规则继续保留；
- 准备提示的微信/QQ 载体和更多外部提醒渠道；
- 完整方案导入与方案审阅工作区、跨方案通用可行性分析；首个切片可以使用预先确认的最小用户方案和下一步行动测试数据；
- 完整日终复盘与三天补记入口、剩余精力建议、方案调整建议的跨场景工作流；
- 多日执行空档、期间执行核对、完整邮件再触达序列；Core / PC 重启后的当前状态恢复仍属于必要异常；
- 全局待决定建议汇总、复杂建议撤销和补偿性调整历史界面；供应商无关建议记录和 LLM 不直接写状态的边界继续保留；
- 桌面活动采集或 ActivityWatch 扩展；v0.1 不采集的决定不变；
- 面向其他地区或医疗用途的合规研究、危机资源本地化和疗效主张；首个 MVP 不作医疗效果承诺。

将这些能力放入“MVP 后”不废弃已经接受的 v0.1 或演进路线决定，只表示它们不进入第一个可验证垂直闭环。黄金路径确认后如发现其中某项确实是闭环必要条件，必须写明证据后再重新分类。

## 当前唯一最高优先级阻塞项

**B-01：确认第一个 MVP 究竟要验证哪一个行为变化。**

它阻塞首个垂直切片，因为当前文档已经为开始、执行、恢复、复盘和建议设计了大量规则，但没有一个被正式选为 MVP 成败的中心。若不先确定核心假设，领域状态模型、验收场景和技术验证都会继续围绕过宽的 v0.1 范围增长。

解决方式是继续一次只问一个问题的 grilling。Windows / Wails 的 V-01 可以并行进行，因为它验证的是已经接受且无论候选黄金路径如何都需要的桌面宿主边界。

## 达到构建就绪后的交接要求

六项门槛全部满足后，构建交接报告至少包含：

- 支持判断的文档、ADR、Issue、spike 和 prototype 证据；
- MVP 精确范围、不做项、黄金路径和必要异常路径；
- 最小领域对象、权威状态、命令、事件和状态转换；
- Given–When–Then 验收场景；
- 尚存但不阻塞构建的风险；
- 第一个端到端实现切片、推荐顺序、每阶段完成条件和验收命令；
- 可推迟到实现反馈出现后的决定。
