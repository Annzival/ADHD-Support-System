## 使用方式

本文件是产品治理检查点，不是产品领域 ADR。每完成一项已确认决定或收到一项 spike / prototype 证据后，都要更新：

1. 六项门槛的状态与证据；
2. 全部未决事项的四类归档；
3. 唯一最高优先级的主 grilling 阻塞项；
4. 可以并行启动、但不能冒充已实现功能的验证任务。

状态只使用：

- **满足**：已有明确决定和足够证据；
- **部分满足**：已有约束，但仍缺少会改变首个垂直切片的信息；
- **未满足**：尚不能据此定义或验收首个垂直切片；
- **等待验证**：问题已被正确分流，必须由独立 spike 或 prototype 提供证据。

达到所有门槛时立即暂停 grilling，并输出构建交接报告。门槛未全部满足，不妨碍独立技术验证先行；验证代码和结果不能计作 MVP 功能完成。

工作在当前产品治理线程和独立 session 之间的稳定路由、依赖与回传规则见 [MVP 构建就绪多 session 编排](mvp-session-orchestration.md)。

## 已确认的核心假设、首要成功行为、使用场景与候选核心闭环

首个 MVP 的一句话核心产品假设已经确认：

> 对已经拥有学习或求职方案、但难以按计划启动的成人 ADHD 用户，在其通过可追溯且须确认的完整方案导入与审阅建立权威用户方案后，状态持久的 PC 执行智能体能否在约定时间主动呈现已确认的下一步行动和低成本状态选择，帮助用户在计划窗口内明确进入一次执行会话，同时不造成不可接受的压力或自主感下降？

首个 MVP 的首要成功行为已经确认：

> 在计划开始时间到来后，用户通过明确操作进入一次执行会话，例如选择“立即开始”或报告“我已经开始”。

改期、今天不做或请求缩小步骤仍是已有产品边界允许的操作，但不计入这一首要成功行为。首个 MVP 不以完成一次执行会话、功能数量、AI 看起来智能或医疗效果作为首要成功指标。

首个 MVP 的首要使用场景也已经确认：

1. 用户可以看到并操作运行本应用的 Windows PC；
2. 用户已经确认一个下一步行动及其计划开始时间；
3. 到达计划开始时间时，用户尚未明确进入对应执行会话；
4. 智能体核心以 PC 作为当时可触达的主动干预载体，帮助用户进入执行会话。

下一步行动本身可以在线上或线下执行，只要求用户当时能够接收并操作 PC 上的开始干预。这是首个验证场景的前置条件，不允许系统通过桌面活动推断用户是否在场。PC 休眠、关机、用户离开 PC 后的恢复触达，以及没有计划开始时间的按需阻碍支持，不属于首要使用场景。

第一轮产品验证的证据边界已经确认：

- 项目作者本人是第一轮唯一验证用户，在自己的 Windows PC 上进行本机单用户 dogfooding；
- 该验证只判断首个闭环对这一名用户是否可用、是否产生值得继续验证的行为信号；
- 结果不得表述为对其他成人 ADHD 用户普遍有效，不据此作医疗、疗效或群体因果结论；
- 外部参与者招募、跨机器分发、遥测、隐私同意流程和群体统计推迟到后续封闭测试。

产品的设计目标仍是拥有既定学习或求职方案的成人 ADHD 用户，而不是只为项目作者定制。第一轮单用户证据用于控制 MVP 范围，不改变后续验证可迁移性的需要。

第一轮产品成功证据采用“单用户可行性信号”，已经确认记录以下维度：

- 符合首要使用场景且开始干预成功送达的机会数量；
- 用户明确进入执行会话的比例和从开始干预到进入会话的时间；
- 用户对干预是否帮助启动的主观判断；
- 用户感受到的压力和自主感是否出现不可接受的恶化；
- 闭环是否可以反复运行，而无须人工修复权威状态。

这些数据用于判断是否值得继续验证，不用于声称应用造成了个人行为改善。第一轮不要求无应用基线、前后因果比较或预设的群体转化率。

进入执行会话的行为信号按已有开始干预生命周期分为两级：

1. **即时进入**：开始干预成功送达后，用户在自己设置的开始宽限时间结束前明确进入执行会话；
2. **延后进入**：开始宽限时间结束后、ADR-0026 定义的未决开始界面失效前明确进入执行会话。

两级均记录从开始干预送达到进入执行会话的准确用时，不新增固定的 15 分钟或 30 分钟阈值。未决开始界面失效后的执行补记继续形成执行证据，但不归入这次开始干预的即时或延后行为信号。未进入仍表示没有观察到该行为信号，不得写成用户失败、拒绝或没有执行。

第一轮 dogfooding 采用低负担、有上限的观察停止规则：

1. 一次**合格机会**是指首要使用场景的前置条件成立，并且系统成功送达开始干预；
2. 观察从第一次合格机会开始；累计至少 5 次合格机会，且分布在至少 3 个不同日期后，即可正常结束；
3. 最长观察 14 个日历日，不为凑足数量额外创建下一步行动或安排开始时间；
4. 14 日结束仍未达到最低数量时同样停止，结果记为“证据不足”，不自动延期，也不记为产品失败或用户失败。

第一轮 dogfooding 同时采用压力与自主感的双层保护机制：

1. 用户可以随时无须说明理由结束本轮验证；
2. 每个出现合格机会的观察日结束时，在验证记录中分别评价压力和自主感，评价选项为“可接受”“令人不适”“不可接受”；
3. 任一维度出现一次“不可接受”，立即结束本轮验证；
4. 任一维度连续两个观察日为“令人不适”，也立即结束本轮验证；
5. 保护性停止后关闭本轮后续主动干预，保留已有证据并记为“保护性提前停止”；该结果不记为用户失败或产品失败，也不自动恢复；
6. 修改产品后需要再次验证时开启新一轮观察，不延续原轮的机会数量或日期累计。

上述评价属于 dogfooding 验证协议，不要求 MVP 首版先实现专门的量表界面。

首个可验证 MVP 采用严格核心假设边界，明确不验证：

- ADHD 诊断、治疗、症状改善或医疗效果；
- 应用是否造成个人行为改善，以及是否对其他 ADHD 用户普遍有效；
- 任务完成率、总产出、专注时长、连续执行天数或长期留存；
- 用户方案本身是否正确，或系统是否能够制定学习、求职策略；
- LLM 是否“聪明”或能否生成高质量的通用建议；
- 通用可行性分析、日终复盘、剩余精力、方案调整、多日重新进入和再触达；
- body doubling、移动端、Web/PWA、服务器模式、多用户、多设备同步和公开分发；
- 通过桌面活动推断用户是否在场、开始或完成。

完整方案导入与审阅是上述严格边界的明确例外：它纳入首个 MVP 的验证范围，并作为正式 dogfooding 前必须通过的独立设置切片。该切片必须产出经用户最终确认的权威用户方案，之后才能开始正式 dogfooding；它有独立的黄金路径与验收场景，但不计入“明确进入执行会话”的首要行为指标。开发期间可以使用预置数据先构建执行闭环，但预置数据只属于技术脚手架，不能代替正式产品验证中的完整导入与审阅。

该决定不改变“系统不制定底层学习或求职方案”的产品边界。必要设置切片遵守 ADR-0015 与 ADR-0035：保留方案原文，区分原文明确信息、Agent 派生内容和缺口，提供可保存的方案审阅工作区，并只在用户最终确认后启用权威用户方案。首要执行闭环继续从“已有且已确认的权威用户方案、下一步行动和开始时间”开始。

必要设置切片的退出条件已经确认：

1. 用户已经在确定性变更确认界面完成最终确认，智能体核心据此启用可追溯的权威用户方案；
2. 已启用方案中至少存在一个经用户确认的下一步行动及其计划开始时间，系统可以直接进入等待首个开始干预的状态；
3. 阻止形成上述可执行安排的关键缺口已经解决；其他非关键不确定信息可以继续明确保留，毋须为了通过设置切片而全部清空。

缺少最终确认、经确认的下一步行动或计划开始时间时，方案导入草案可以保存并稍后继续，但必要设置切片尚未完成，不能开始正式 dogfooding，也不能触发任务调度或主动干预。

第一项下一步行动及计划开始时间采用“原文优先、Agent 可以提议、用户逐项确认”的产生规则：

1. 方案原文已经明确给出可执行行动或时间安排时，系统将其作为带原文依据的候选；
2. 原文缺少足够具体的行动或时间时，Agent 可以在用户既有方案边界内提出任务拆分或时间分配，但必须明确标为派生内容并提供对应原文依据；不得自行新增目标、截止日期或优先级；
3. 用户可以直接编辑候选，并须在启用方案前明确确认第一项下一步行动及计划开始时间；整体确认不能代替这两个字段的明确确认；
4. 未完成明确确认时，工作区保持为可保存草案，必要设置切片尚未完成。

该规则只确定权威安排的来源和确认边界，不提前决定方案审阅工作区的视觉布局或控件形式。

必要设置切片的黄金路径已经确认：

```text
用户导入文本或 Markdown
  → 系统立即保存方案原文，并建立可保存、可退出的处理状态
  → Agent 生成可追溯的方案导入草案
  → 方案审阅工作区分别展示原文明确信息、Agent 派生内容和缺口
  → 用户编辑草案、解决关键缺口，并逐项确认第一项下一步行动及计划开始时间
  → 用户选择启用方案
  → 确定性变更确认界面展示即将创建或更新的内容、仍保留的不确定信息和来源区别
  → 用户最终确认
  → 智能体核心原子地启用权威用户方案及首项执行安排，并进入等待开始干预的状态
```

用户在处理或审阅阶段保存并退出时，系统保留方案原文和当前草案，之后可以继续；这属于正常的中途退出，不算必要设置切片已经完成。黄金路径只固定交互与状态变化的顺序，不固定工作区布局、控件或视觉样式。

必要设置切片只保留以下四类会影响权威状态正确性的异常：

1. **Agent 或模型不可用**：保留方案原文和已经保存的草案，明确显示设置尚未完成；用户可以稍后重试或更换模型配置，但系统不得启用方案；
2. **方案原文在草案生成后发生修改**：基于旧版原文的草案和未确认建议标记为已被取代，必须基于新版原文重新生成或审阅；
3. **关键缺口或首项执行安排尚未确认**：允许保存退出，但保持草案状态，不创建调度，也不发起主动干预；
4. **最终确认时发生版本冲突或持久化失败**：整个启用操作失败并回滚，保留可继续处理的草案，不允许出现部分方案已启用或调度先于方案生效的状态。

输入大小、编码、重复导入、具体重试次数、错误文案和视觉呈现留到实现中决定。用户主动保存退出已经属于正常路径，不重复作为异常。

这些不做项只裁剪首个可验证 MVP，不废弃已经接受的 v0.1 或未来路线图决定。首个 MVP 不包含“现在有点难开始”分支和完整 LLM 阻碍支持；相关 v0.1 决定与 Agent 边界继续保留，待首个确定性闭环验证后再实现和验证。

首要执行闭环的终点已经确认：用户完成或暂停执行，并完成或跳过一次收尾确认后，系统保存执行证据；暂停时同时保存恢复包；随后退出当前执行会话，回到可以继续调度的稳定状态。用户跳过收尾确认时，系统仍须根据已有明确操作保存一致的最小执行证据并结束会话，不得留下悬空执行状态。

“明确进入执行会话”仍是首要产品成功指标；把完成、暂停和收尾纳入闭环，只用于保证该闭环能够完整退出并反复运行，不把任务完成率提升为成功标准。日终复盘、剩余精力扩展和下一项工作不进入首要执行闭环。

首要执行闭环采用以下确定性黄金路径：

```text
已有经确认的权威用户方案、下一步行动及计划开始时间
  → 到达计划开始时间，且系统没有开始、完成或改期记录
  → 智能体核心创建并送达一次开始干预
  → 用户选择“立即开始”
  → 智能体核心原子地建立执行会话，并按预计时长建立一个会话检查点
  → 检查点前不周期性追问，用户执行该下一步行动
  → 用户在检查点前或检查点到达后报告完成
  → 系统提供一次可跳过的收尾确认
  → 系统保存执行证据、结束执行会话，并回到可继续调度的稳定状态
```

黄金路径之外，首个 MVP 保留以下四个确定性的开始状态校正分支：

1. **“我已经开始”**：用户明确校正为已经在执行；它与“立即开始”是两个独立操作，不得合并，也不得被解释为已经完成。首个 MVP 不要求用户补充大致开始时间；
2. **“我已经完成”**：用户明确校正为已经完成，随后进入同一套可跳过的收尾确认和稳定退出；
3. **“改到具体时间”**：用户确认新的计划开始时间，系统结束当前开始干预并建立新的执行安排；
4. **“今天不做”**：系统记录用户对本次执行安排的明确决定并结束当前开始干预，不自动修改权威用户方案。方案影响分析和方案调整建议不进入首个 MVP。

这四项用于让权威状态与用户明确报告的现实一致，不改变“立即开始”作为黄金路径和“明确进入执行会话”作为首要成功行为。

进入执行会话后，首个 MVP 采用以下用户控制的确定性分支：

1. 用户在检查点前可以随时报告完成，或暂停并保存恢复包；
2. 检查点到达时，系统只提供“已经完成”“继续并确认下一检查时间”“暂停并保存恢复包”三类确定性操作；“请求阻碍支持”不进入首个 MVP；
3. 用户选择继续时保持同一执行会话，只替换下一检查点，不结束后重新建立会话；
4. 续行可以再次发生，但每一次都必须由用户明确确认新的检查时间，系统不得据此建立自动周期性追问；
5. 用户完成或暂停后，进入同一套可跳过的收尾确认，保存执行证据；暂停时同时保存恢复包，随后结束当前执行会话并回到稳定状态。

无回应仍不混入黄金路径，其最小必要路径继续由 B-02 裁剪。首个 MVP 不包含“现在有点难开始”分支和完整 LLM 阻碍支持；准备提示、日终复盘、剩余精力和下一项工作也不进入该路径。黄金路径不依赖 LLM 生成结果。

候选必要异常仅包括：

- 用户未回应开始干预，系统停止主动跟进并保留/过期正确的被动入口；
- 模型不可用，确定性开始、改期、暂停和退出操作仍然可用；
- 智能体核心或 PC 重启，权威状态和调度可恢复，过期干预不补发；
- 非法或基于旧版本状态的转换被拒绝，权威状态不被破坏。

多日重新进入、日终复盘、剩余精力、邮件再触达等已确认能力是否进入后续切片，不影响上述候选闭环能否先被构建和验证。完整方案导入与审阅已经明确为 dogfooding 前必须通过的独立设置切片，不与下述可重复执行闭环合并计算行为信号。

V-01 与其最小关闭恢复复验 V-01R 已完成。产品治理线程结合 PR #13 和 PR #15 的结果接纳：Wails 五项桌面能力、通知上下文返回和薄宿主边界在锁定环境中具有足够的实机 `PASS` 证据，可以继续保留 Wails v3 作为 v0.1 首选桌面宿主。该结论不外推到其他 Windows、Wails 或 WebView2 版本，也不把 spike 代码计作 MVP 功能完成。

产品治理线程已结合 Issue #18、PR #24、Windows 实机脱敏证据及两轮双轴复审接纳 V-03 的最终 `PASS`。该结论覆盖锁定环境中的最小合成 SQLite 事务与恢复机制：已提交状态在正常与受控异常退出后保持一致，未提交写入不形成半更新；未来动作与合并恢复信号保持幂等，过期记录不补发；一次真实 PC 重启后只出现一个宿主和一个 Core，并从同一 SQLite 身份恢复。Windows 成功证据继续且仅锚定 `1ca7d92`；后续 `2efbb3c` 只修复并自动验证 bootstrap 超时失败路径，没有被表述为新的 Windows 实机证据。

V-03 不覆盖异常断电、数据库加密、备份恢复、其他 Windows 版本、多用户或多设备，也不定义 B-03 的正式领域对象、状态或失效语义。结合 V-01/V-01R、V-02 与 V-03，门槛 5 的既定高风险技术验证已经满足；这些 spike 代码和证据仍不计作 MVP 功能完成。
