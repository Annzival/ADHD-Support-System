# 为已启用用户方案提供显式和关键变化触发的可行性分析

每个已启用用户方案都必须提供一个固定、可发现的“通用可行性分析”入口，用户可以从该方案的主窗口上下文直接发起分析。入口不能只存在于 Agent 对话、隐藏菜单或自动触发流程中；具体视觉位置留给后续界面设计。

除用户主动请求外，系统只在用户方案启用或实质修改、截止日期或依赖关系或可用时间变化、新执行证据使原估时或安排可能失效，以及执行空档已经产生实质影响时运行分析，不在每次完成下一步行动后自动进行完整分析。

## 确定性检查

智能体核心先计算截止日期与剩余可用时间、未完成工作与依赖关系、已确认执行安排重叠、估时与实际用时偏差，以及必要信息缺口。只有需要解释、权衡或生成修改候选时才调用 LLM。结果明确区分确定冲突、可行性风险、信息不足和仍然可行，不得把风险写成确定失败。

用户主动请求或正在编辑方案时，结果在当前主窗口上下文呈现。后台状态变化首次发现新的实质风险时，可以按照 ADR-0031 产生一次非阻塞建议注意请求；没有新问题时不发送“方案仍然可行”的通知。同次分析最多突出三个最影响执行的事项，其余结果留在方案上下文中被动查看。

## 建议与应用

每个问题展示依据事实与执行证据、受影响的截止日期或依赖或执行安排、未知信息，以及最多三个调整候选。候选只能调整拆分、估时、时间分配、顺序或暂停状态，不得替用户制定新的学习或求职策略。

分析结果不直接修改用户方案；用户采用候选前使用确定性变更确认。用户方案、依赖数据或相关执行证据变化后，旧分析和建议标记为已被取代。模型不可用时仍显示确定冲突和信息缺口，但不生成 Agent 调整候选。
