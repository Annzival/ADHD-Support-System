# V-05 恢复干预载体映射 prototype 结果

> **结论：PASS（仅限一次性低保真 UI prototype）。**
>
> 方案 D“主窗口主入口、系统通知辅助、上下文独立展开”最符合本次用户走查证据。它不是生产实现、正式状态机或 MVP 已就绪结论。

## 验证问题与边界

本任务验证的是：恢复后，如何映射“触发状态 → 主动或被动载体 → 可用操作 → 主窗口上下文 → 失效或降级方式”，使用户能低压力地区分上次执行上下文和当前计划，并选择继续上次、处理上一项、按当前计划继续或暂不决定。

本分支只包含浏览器内存中的模拟 UI；没有接入 Wails、Python Core、SQLite、真实 Windows 通知或置顶行为，也没有定义正式 API、数据库、命令或状态机。prototype source 明确标注为非生产实现，保留在独立分支 `codex/prototype-v05-recovery-carriers`。

## 方案比较

| 方案 | 主要结构 | 第一轮 / 第二轮观察 | 结论 |
| --- | --- | --- | --- |
| A：主窗口主导 | 通知只负责发现；主窗口并排解释和决策 | 上下文清楚、压力低、抢焦点风险低；但用户偏好 C 的进入方式 | 保留为对照，不推荐为最终组合 |
| B：置顶小窗主导 | 小窗先给有限选择，主窗口补充完整上下文 | 压力中等，用户感到可能抢焦点；关闭后再次打开小窗的路径不清楚 | 不作为恢复主载体 |
| C：系统通知主导 | 通知直接选路线，主窗口显示路线 | 压力低、抢焦点风险低，是前三案中用户偏好；但通知作为唯一直接入口不可靠，且原型曾把两个上下文做成互斥呈现 | 提供 D 的低压力路线结构，但不单独采用 |
| D：主窗口主入口（混合） | 主窗口固定恢复入口；通知只跳转到同一入口；上次 / 当前可独立展开 | 第二轮四项核对均通过；随后用户明确要求两个完整上下文能够同时保留，已按此收敛 | 推荐 |

方案 D 不是新的第一轮候选，而是由第一轮明确反馈支持的唯一混合方案，符合 Issue #7“第一轮最多三案、只有明确反馈才做一个混合方案”的退出约束。

## 六个场景与证据

| 场景 | prototype 中可观察的结果 | 用户证据 | 静态状态核验 |
| --- | --- | --- | --- |
| 1. 活动执行会话 + 当前计划推进 | 提供“继续上次执行 / 按当前计划继续 / 暂不决定”；两类上下文分开呈现 | A、B、C 均走查；用户偏好 C。D 的主窗口可直接进入和上下文区分在第二轮通过 | A–D 均渲染；D 可同时展开两条上下文 |
| 2. 恢复包 + 当前计划推进 | 恢复包和当前计划区分，不把恢复包写成失败或当前计划 | 用户实际体验 C，认为与场景 1 一致、没有额外问题 | A–D 均渲染、可操作 |
| 3. 只错过计划开始（没有开始证据） | 只有“处理上一项”，不出现“继续上次执行” | 用户实际体验 C；D 第二轮确认该限制通过 | D 断言没有 `continue-last`，有 `handle-previous` |
| 4. 多个失效干预合并 | 显示三个旧干预合并成一次当前入口，不逐条补发 | 用户实际体验 C，认为与场景 1 一致、没有额外问题 | A–D 均渲染；模拟状态显示一个当前入口和 `oldInterventionsReplayed: false` |
| 5. 已选择“按当前计划继续” | 主窗口只显示当前计划；上一项仍明确为未知 | C 走查确认上一项为未知；D 第二轮再次确认 | D 断言上一项结果仍含“未知” |
| 6. 暂不决定后寻找被动入口 | 主动呈现结束；主窗口保留安静的单一恢复入口，不补发旧干预 | C 走查确认可找到安静入口；D 第二轮确认没有重复面板 | D 断言重新进入后只有一个“恢复入口” |

用户在第二轮指出：原先 D 的两个“查看”入口实际表现成互斥切换。该反馈澄清了“不是互斥”的含义：两个完整上下文应能同时保留。为遵守“两轮体验”上限，随后仅进行了机械的代码收敛和静态契约核验，没有虚构第三轮用户体验。

## 推荐载体映射：方案 D

| 触发状态 | 主动 / 被动载体 | 可用操作 | 主窗口上下文 | 失效或降级方式 |
| --- | --- | --- | --- |
| 存在活动执行会话，且当前计划已有适用行动 | **主窗口首页恢复入口**为主要载体；系统通知只提供“打开恢复选项”的辅助跳转；恢复用置顶小窗不承担选择 | 继续上次执行、按当前计划继续、暂不决定 | 用户可分别展开“上次执行上下文”和“当前计划”，两者可同时完整显示；选择后只显示所选上下文 | 通知被取消或忽略不阻断主窗口入口；不抢焦点；旧干预不补发 |
| 存在恢复包，且当前计划已有适用行动 | 同上 | 继续上次执行、按当前计划继续、暂不决定 | 恢复包明确是上次执行上下文，不等同当前计划或失败 | 同上；选择当前计划不会删除恢复包或写成放弃 |
| 只错过计划开始，且没有开始证据 | 同上 | **处理上一项**、按当前计划继续、暂不决定；不提供继续上次执行 | 上一项标为未知，打开的是核对路径，不暗示未开始、拒绝、失败或放弃 | 沉默维持未知；不把旧开始干预重发为队列 |
| 多个旧干预已经失效 | 合并为**一个当前恢复入口**；主窗口为主，通知仅为可忽略的辅助跳转 | 对当前仍需辨认的最近上下文提供处理上一项 / 当前计划 / 暂不决定 | 不逐条呈现或要求逐项处理旧干预；显示合并事实 | 旧干预保留为失效记录；`oldInterventionsReplayed` 为 false |
| 已选择按当前计划继续 | 无新的主动载体 | 本次恢复选择结束 | 只显示当前计划；上一项的结果在模拟状态中仍为未知 | 不生成“已放弃”或“未开始”暗示；本 prototype 不定义之后的正式补记路径 |
| 已选择暂不决定 | 无主动通知或弹窗；主窗口首页保留静态**被动恢复入口** | 主动打开后仍可继续上次 / 处理上一项（按当时上下文）/ 按当前计划继续 / 再次暂不决定 | 重新进入后可独立展开两条完整上下文；只有一个恢复选择面板 | 不闪烁、不红点、不补发旧干预；被动入口不是一次新的干预 |

这张表是 UI prototype 的推荐映射，不是正式领域行为定义。尤其是“当前仍需辨认的最近上下文”的选择规则不能由本原型替 B-03 定义。

## 判定依据

`PASS` 适用于 Issue #7 所定义的 prototype 范围，理由如下：

1. A、B、C 三种结构明显不同的方案可用 URL 和底部切换栏运行；D 是受反馈支持的一项混合方案。
2. 六个规定场景均有可操作的模拟状态和操作后状态；用户体验和静态核验共同覆盖了题目要求的关键判断。
3. 用户能区分“继续上次执行”与“处理上一项”，并确认“按当前计划继续”不会把上一项改写为放弃。
4. 用户能在“暂不决定”后找到主窗口中的安静入口；D 消除了此前的重复操作面板。
5. 推荐映射不引入 LLM、缩小步骤、阻碍支持、正式持久化或新的产品范围，也不覆盖 ADR-0012、ADR-0013、ADR-0016、ADR-0026 的既有约束。

## 限制、风险与回传事项

### 不由本任务证明的事项

- 模拟通知无法证明真实 Windows 通知的动作数量、取消方式、焦点顺序或可发现性；模拟小窗也不证明真实置顶行为。方案 D 刻意不依赖它们作为恢复的唯一入口，因此这些不是本次推荐映射的关键未决判断。
- prototype 不验证视觉精修、辅助技术、真实窗口尺寸或生产端响应式布局。两个上下文在小尺寸下的正式排布需要实现阶段重新设计。
- 第二轮最后的“同时展开”收敛依据是用户的明确意图，之后仅做了静态核验；没有宣称用户已体验这次最后的机械修正。
